0. ZAMIAR I DLACZEGO WERSJA 2 BYŁA ZŁA
=====================================================================
Zamiar (z poleceń): nie „uporządkować projekt tak, jakby był skończony”,
tylko zbudować BAZĘ, na której gra urośnie (baza/hub, więcej demonów,
bossów, broni, zaklęć, map, trybów) bez cofania się i zmieniania
fundamentów. Czytelność jest skutkiem ubocznym, nie celem.

Błąd wersji 2: oceniała ECS i kolejkę zdarzeń względem DZISIEJSZEJ
skali (jedna arena) i odrzucała je jako „niepotrzebne teraz”. To jest
dokładnie decyzja, która później wymusza przebudowę fundamentów.
Wersja 3 przyjmuje je jako fundament i rozwiązuje oba realne problemy,
które w wersji 2 posłużyły za powód odrzucenia:
  - ECS a 4000 miejsc kodu i testów czytających płaskie pola (e.x, e.hp):
    ECS NA PŁASKICH BYTACH (sekcja 3). Komponent to zadeklarowany zestaw
    pól bytu, systemy wybierają byty po komponentach. To idiomatyczny
    model Lua (jak biblioteka tiny-ecs) i nie wymaga przepisania odczytów.
  - Kolejka zdarzeń a kolejność skutków: magistrala DWUFAZOWA (sekcja 5).
    Faza symulacji wykonuje słuchaczy natychmiast, w zadeklarowanej
    kolejności (deterministycznie); faza prezentacji jest kolejką
    opróżnianą po kroku i nie może zmienić symulacji.
Prototyp na LÖVE 11.5 potwierdził wydajność, determinizm i kolejność
(sekcja 11).

3. ECS NA PŁASKICH BYTACH
=====================================================================
Byt: tablica { id, has = {komponenty}, ...pola komponentów }.
Komponent: nazwa + schemat pól (typ, wartość domyślna, opis, właściciel).
Prefab: lista komponentów + wartości z definicji (Type Object: byt
wskazuje na swoją definicję, def). Zapytanie: world:query('health',
'guard') — lista w kolejności tworzenia, przeliczana tylko po zmianie
struktury. Zmiany struktury (spawn, destroy, dodanie komponentu) są
odraczane do końca systemu → brak modyfikacji listy w trakcie iteracji.
Tryb ścisły w testach: zapis pola spoza zadeklarowanych komponentów bytu
= błąd (koniec pól dopisywanych „po drodze” — dziś 107 pól demona w 15
plikach).

Komponenty (z obecnych pól, każde pole ma jeden dom):
  identity     id, def, kind, variant, displayName, tier*, rewardId
  transform    x, y, z, facing, yaw
  collider     radius (z ciała), mass
  motion       vx, vy, vz, pushX, pushZ, walkVX, walkVZ, walkSpeed, walkAt,
               walk, blocked, slamLock, collideLock
  health       hp, maxHp, armorRating, locationArmor, resistances, immune,
               soak, zones, woundFlash
  guard        poise, guardQuiet, staggerLock, stun, heavyStagger,
               knockedDown, knockTime, breakFlash, hitPause
  conditions   conditions
  brain        ai, phase, recover, attack, decision, side, threat
  perception   sense, visible, memory, awake, lastX, lastZ, path, pathTimer
  attacker     attackSpec, attackKind, attackCount, restUntil, aimX, aimZ,
               windup, windupDuration, didHit, pendingHazard, packetCache
  rush         rushVX, rushVZ, rushScale, lungeX, lungeZ, chargeTime
  flight       leaping, leapY, leapVX, leapVY, leapVZ, landings
  evade        evadeTime, evadeReady, evadeSide, evadeX, evadeZ, evades
  corpse       deathTime, fallY, fallVY, fallLanded, deathResponse
  appearance   hit, flinch, flinchSide, flinchLeanV, spawnAge, previewFrame
  tags         boss, dummy, armored
  (gracz)      knight (tarcza, nietykalność, unik, ślizg, skok), intent,
               inventory (sloty broni; adapter na pola zapisu mag, reserve,
               revolverMag, revolverReserve), abilities (ładunki, czary)
  (inne)       projectile, hazard, pickup, gate (portal), lifetime

Dlaczego to skaluje: nowy byt (np. wieżyczka, sojusznik, przedmiot
interaktywny w bazie) to nowy prefab z istniejących komponentów; nowa
zdolność to nowy komponent + system, bez dotykania reszty.

=====================================================================
4. SYSTEMY I HARMONOGRAM
=====================================================================
Scheduler: nazwane fazy, systemy w jawnej kolejności (dzisiejsza
session/simulation.lua staje się jego konfiguracją, ta sama kolejność).
  input/intent → knightMotion → weapons (spust, salwa) → perception →
  brain (State: AI.states) → locomotion (Strategy: AI.styles) →
  actions (Strategy: rodzaje dostarczenia) → flight → projectiles →
  hazards → contacts (pchnięcia, mury, domino) → balance (garda, stany,
  timery) → corpses → director/spawner → mode progression
  → [flush 'present'] → animation → render → ui
Każdy system: jedna odpowiedzialność, zapytanie o komponenty, stałe
z tuning, zdarzenia zamiast bezpośrednich efektów.

5. ZDARZENIA (magistrala dwufazowa)
=====================================================================
  'sim'      słuchacze wykonywani natychmiast w systemie, który emituje,
             w kolejności (priorytet, potem rejestracja). Mogą zmieniać
             symulację. Przykład: zabicie → (10) leczenie za przełamanie
             → (20) nagroda → (30) reżyser tempa.
  'present'  kolejka opróżniana raz po kroku symulacji: dźwięk, cząstki,
             kamera, puls ramki, napisy, pomiary. Tylko odczyt symulacji
             (w testach wymusza to tryb ścisły).
Katalog zdarzeń (schemat ładunku w rejestrze, nieznane = błąd):
  ShotFired, VolleyResolved, BodyHit, GuardBroken{heavy}, Countered,
  KnockedDown, Tripped, Crippled, Wounded, EnemyKilled{offBalance},
  PlayerHit, PlayerStaggered, PerfectDodge, WallSlam, BodiesCollided,
  AttackTelegraphed, AttackReleased, AttackCancelled, Landed, Evaded,
  PortalOpened, EnemyArrived, WaveCleared, PickupTaken, ConditionApplied,
  ModeChanged.
Dziś 80 bezpośrednich wywołań efektów w kodzie symulacji (Audio, FX,
g:burst, Weight, Telemetry) → stają się słuchaczami 'present'.
Dlaczego to skaluje: nowy efekt, osiągnięcie, samouczek, statystyka,
narrator, dźwięk — dopisuje słuchacza, nie dotyka systemów.

6. DANE: SCHEMATY I DZIEDZICZENIE
=====================================================================
Każda definicja przechodzi: extends (łańcuch rodziców) → wartości
domyślne schematu → walidacja → zamrożenie (tylko odczyt).
  Body       wspólne dla demonów i rycerza (hp, armor 0, soak 0, resist {},
             mass 1, poise 36, woundAt .45, radius .25, aimY 1.1, struck,
             blood, stability = √mass, brace, stagger...)
  Creature   body + move (styl) + actions + nagroda + atlas; Boss = szablon
             (boss, stability 1.5, maxAttackers 1, woundAt 1, microStun);
             fazy bossa jako lista stanów (przygotowane na przyszłość)
  Action     JEDEN format dla ataków demonów i umiejętności gracza:
             dostarczenie (melee/lunge, rush/charge, leap, projectile, fan,
             area/pool, strike/mark, throw) + ładunek (pakiet obrażeń, stan,
             impuls) + zapowiedź (windup, telegraf) + koszt/odnowienie.
             Ładunek prochowy gracza staje się Action — tak samo dojdą
             zaklęcia.
  Weapon     Firearm (wspólne) → strzelba, rewolwer; fire, mechanism,
             attack (ładunek), glyphs, amunicja
  Knight     Body + bryła trafień + tarcza + unik + ruch
  Condition  efekty (speed, recovery, damage over time, tick), stos
  Encounter  fale, stada, reżyser; Level: układ areny, portale, światła
  Mode       które systemy, który świat, które ekrany, postęp
Plik demona zawiera tylko różnice:
  return Creature.define({ id = 'armored', extends = 'imp',
    name = 'Iron Thrall', souls = 12,
    body = { hp = 170, armor = 60, mass = 1.4, woundAt = 0.40, struck = 'metal' },
    move = { speed = 3.0, accel = 12 },
    actions = { claw = { hyper = 2, packet = packet(15, 70) },
                shoulder = Action.charge({ ... }) } })

=====================================================================
7. TRYBY, USŁUGI, ZAPIS, POWTÓRKI
=====================================================================
Tryby (State + Strategy): rejestr trybów (skirmish, poligon, wyprawa,
  baza). Tryb składa świat (Level), zestaw systemów, ekrany i postęp.
  Stos scen (menu → tryb → pauza) zamiast porównań g.state w wielu
  miejscach. Baza/hub = nowy tryb, nie przeróbka.
Usługi (kontekst sesji, Dependency Injection): rng symulacji (ziarno
  sesji, deterministyczny), rng prezentacji (cząstki, warianty dźwięku),
  zegar, audio, zapis, wejście. Żadnych globali; testy podstawiają usługi.
Zapis (Memento): każdy komponent deklaruje, co się zapisuje; adapter
  zachowuje obecny format zapisu wyprawy. Później: zapis pełnego stanu.
Powtórki (Command): wejście gracza jako komendy z numerem kroku; ten sam
  mechanizm napędza złoty wzorzec, boty i (w przyszłości) powtórki.
